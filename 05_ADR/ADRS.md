# ADRs

## ADR-001 — Eclipse Theia as IDE platform
**Context**: Need VS Code-like IDE in browser and desktop, extensible, self-hostable. **Decision**: Theia (browser + Electron targets, VS Code extension compatibility via Open VSX). **Alternatives**: code-server/OpenVSCode Server (browser-first, weaker desktop/product customization story, licensing/branding constraints), building on Monaco directly (too much to rebuild). **Consequences**: + one codebase for both modes, DI extension model; − Theia upgrade churn, internal API changes, not all MS extensions available.

## ADR-002 — Broker SSH from trusted backend
**Decision**: Hosted SSH only via the connection broker; browser gets single-use tickets and a WS stream; runtimes have no lab egress. **Consequences**: + central policy, host-key checks, audit, revocation; − broker is security-critical and must be capacity-planned.
**Addendum (2026-10-17, spike S4 — [report](../docs/spikes/S4_SSH2.md))**: `ssh2` 1.17.0 confirmed as the SSH library (PTY, exec, SFTP, jump hosts, agent keys; 20/20 checks against OpenSSH 9.6). Binding rules for `packages/broker-core`'s `SshTransport`: (1) **`hostVerifier` is mandatory** — `ssh2` accepts any host key when it is absent; the wrapper refuses to connect without one and a test asserts it; (2) the verifier compares OpenSSH `SHA256:` fingerprints and decides `HOST_KEY_UNKNOWN` vs `HOST_KEY_MISMATCH` itself (proven: a mismatch ends the connection before any `USERAUTH_REQUEST`); (3) interrupts are sent as `\x03` through the PTY — the SSH `signal` request did not interrupt a foreground job; (4) each jump-host hop is pinned separately; (5) algorithm lists are pinned explicitly; (6) `ssh2` errors map to `ErrorCode`s by level (`handshake`, `client-authentication`, `client-timeout`, `client-socket`) as tabulated in the report.

## ADR-003 — Modular monolith
**Decision**: Deployables: control-plane, broker, runtime image, desktop app. Strict package boundaries enable later splits. **Consequences**: + simpler ops/debugging; − discipline required on boundaries (lint-enforced).

## ADR-004 — Pod per workspace
**Decision**: Each running workspace = one pod + PVC (hosted); Docker container + volume (local/dev). **Alternatives**: multi-user shared Theia backend (weak isolation), VMs per workspace (cost/latency; consider later via Kata). **Consequences**: + isolation, quotas; − cold-start latency (mitigate with image pre-pull, idle stop/resume).

## ADR-005 — Workspace routing: path-based `/w/{id}/`
**Status**: Accepted — 2026-10-17 after spike S2 ([report](../docs/spikes/S2_REVERSE_PROXY.md)); ratify in the PR review. **Options**: (a) path `/w/{id}/` through the control-plane router; (b) subdomain `{id}.ws.<corp>` with wildcard TLS. **Evidence**: both work with Theia 1.76 unchanged (frontend URLs and the Socket.IO path derive from `location.pathname`). Path routing has one proven defect, fixed at the gateway: Theia's per-backend `theia-connection-token` cookie is `Path=/`, so two workspaces on one origin overwrite each other and the first one gets `403` on reconnect; rewriting `Set-Cookie` to `Path=/w/{id}/` fixes it (2/2 runs each way). **Decision**: (a) path-based — it matches the existing contract (`ideUrl: "/w/{id}/"`), needs one IDE host plus a `*.webview.<host>` wildcard certificate (Theia webview origins are `{{uuid}}.webview.{{hostname}}` and keep the `/w/{id}/` path), and a host cookie for the gateway session. **Gateway requirements (Phase 05)**: authorize every HTTP request and WebSocket upgrade per workspace (404 when not visible); rewrite runtime `Set-Cookie` paths to `/w/{id}/`; 308 `/w/{id}` → `/w/{id}/`; serve `/favicon.ico` at the root; 404 anything else; route `*.webview.<host>/w/{id}/…` to the same runtime. **Consequences**: + simplest DNS/TLS, no contract change; − a user's workspaces share one browser origin (code in one workspace's frontend can call another of the *same user's* workspaces; storage is shared), mitigated by the extension allowlist (ADR-010); revisit subdomains if the Phase 14 threat-model review requires origin isolation between workspaces. Webviews through the proxy still to be exercised in Phase 02.

## ADR-006 — Remote terminal & FS approach: Theia frontend extension (option B)
**Status**: Accepted — 2026-10-17 after spike S3 ([report](../docs/spikes/S3_REMOTE_TERMINAL_FS.md)); ratify in the PR review. **Options**: (A) VS Code API plugin (Pseudoterminal + FileSystemProvider) as a web extension so it runs in the frontend; (B) Theia frontend extension: `TerminalWidget` in pseudo-terminal mode + `FileSystemProvider` registered through a `FileServiceContribution`; (C) standalone xterm widget. **Must satisfy**: P9 (no SSH reachability from runtime), browser/Electron parity, upgrade resilience. **Evidence**: both A and B were built against a stub of the session contract and run side by side on Theia 1.76. In the browser both pass (remote terminal at the widget's real size, Ctrl+C → exit 130, remote file open/edit/save) and both talk to the broker from the page (`Origin` of the IDE), never from the runtime. In Electron, B passes the same checks; **A never runs**: Theia skips the frontend plugin host on Electron, and a plugin with a `browser` entry is always assigned to that host, so a dual-entry build does not help; a Node-only build would run in the backend plugin host, which in hosted mode is the workspace runtime (P9). **Decision**: (B). `qe-remote` is a Theia frontend extension: remote terminals are Theia terminal widgets with `isPseudoTerminal` wired to the broker stream, remote files are a `qe-ssh://` `FileSystemProvider` registered by a dependency-free `FileServiceContribution` (one that injects services needing `FileService` creates a DI cycle and the frontend fails to start). The transport sits behind the `ConnectionClient` interface bound per mode: hosted/local-web → broker over HTTPS/WebSocket from the frontend; desktop → relay over Theia RPC to the Electron backend (embedded broker for personal targets, hosted broker with the user's Bearer token for managed targets), because the Electron renderer runs from `file://` (WebSocket `Origin: file://`) and tokens stay in the main process (T22). (C) not needed — B already uses Theia's xterm widget without a backend process. **Consequences**: + P9 kept, one code path for browser and Electron, Theia terminal features, DI-bound clients per mode; − relies on Theia internals (`TerminalService.newTerminal({ isPseudoTerminal })`, `FileServiceContribution`, file system provider interfaces) — the same seams Theia's own VS Code API layer uses, so they are unlikely to change silently; pin Theia and run the S3-style end-to-end check on every upgrade (R2, R13). Follow-ups: broker queues input until the shell is ready and maps `signal` to `\x03` (Phase 08); `ifMatch` on `fs/write`, SFTP whole-second `mtime` limits the ETag (Phase 09); WebSocket/HTTP without `Origin` accepted only with Bearer auth, never with the cookie (Phase 08 contract addendum).

## ADR-007 — Short-lived SSH certificates
**Decision**: Default credential = ephemeral key signed by Vault SSH CA (TTL ≤ 15 min, user principal). Fallback: Vault-stored key per target. **Consequences**: + no long-lived keys, per-user attribution on targets; − targets must trust CA (onboarding script).
**Addendum (2026-10-17, spike S4)**: Works end-to-end with Vault 2.2 (ed25519 CA) and OpenSSH 9.6 — wrong-principal and expired certificates are rejected by the target — **but `ssh2` 1.17.0 needs a 5-line patch** (it writes the certificate algorithm name into the signature blob). Carry the patch (`patch-package`), submit it upstream, pin `ssh2` exactly and guard it with an integration test; the `vault_key` fallback needs no patch. Certificates in an agent are not used by `ssh2`, so the broker keeps the ephemeral key in memory only. Set the Vault role's `key_id_format` to include the user identity — the default `vault-token-<hash>` is what target sshd logs.

## ADR-008 — Shared broker-core
**Decision**: Same library for hosted broker and embedded (desktop/local) broker with injected TargetSource/CredentialSource/HostKeyStore/AddressGuard/AuditSink. **Consequences**: + parity, one tested SSH stack; − careful dependency boundaries.

**Addendum — Phase 10 (2026-10-28), dependency boundaries.** The embedded broker runs in two backends of the
`qe-remote` extension: `src/electron-node` (desktop, always) and `src/node` (the browser app's backend, bound only
when `QE_MODE=local-web`, so a hosted workspace runtime never reaches SSH targets itself — rules 2 and 3). Both are
their own lint elements and may import `broker-core`, `policy` (the organisation's deny list for personal targets),
`qe-core` (the environment) and the extension's own `common` code; frontend code of the extension still may not.
The hosted broker's user-facing error messages (`messageFor`) and per-operation file request handling
(`fileOperation`) move into `broker-core` so both brokers answer identically (09_LOCAL_AND_WEB_PARITY §2).

## ADR-009 — npm workspaces
**Decision**: npm workspaces (Theia CLI expects hoisted node_modules). pnpm only with hoisted linker after spike. **Consequences**: simpler Theia builds; slower installs mitigated by CI cache.

## ADR-010 — Internal Open VSX mirror
**Decision**: Extensions only from an internal Open VSX instance with an allowlist; no public marketplace in hosted builds. **Consequences**: + supply-chain control; − mirror operations and extension request process.

## ADR-011 — Workspace package conventions (ESM, source export condition, declared graph)
**Status**: Accepted — implemented in Phase 01 on 2026-10-17; ratify in the Phase 01 PR review. **Context**: The kit's package template points `main`/`types` at `dist`, so tests and lint would need a build first and could silently read stale output; an unresolvable workspace import is treated as external by the boundaries plugin and would slip past the dependency rules. **Decision**: Library packages in `packages/*` are ESM (`"type": "module"`, `NodeNext`). Each exports `{ "@qe/source": "./src/index.ts", "types": "./dist/index.d.ts", "default": "./dist/index.js" }`; TypeScript (`customConditions`), Vitest (`resolve.conditions`) and the ESLint import resolver (`conditionNames`) use `@qe/source`, Node uses `dist` at runtime. A workspace dependency is declared in three places — the import, `package.json` `dependencies`, `tsconfig.json` `references` — and `tests/lint/workspace-graph.test.ts` enforces agreement, because TypeScript does not fail on a missing reference when it can resolve the source. Theia extensions (Phase 02) keep CommonJS + decorators in their own `tsconfig.theia.json`. **Alternatives**: `paths` aliases (duplicate the graph, leak into emitted code); build-before-test (slow, stale-output risk). **Consequences**: + lint/test work on a fresh clone, one source of truth per package, runtime unaffected; − the custom condition must be repeated in each tool's config, and adding a dependency touches three files (guarded by the test).

## ADR-012 — IDE build and extension supply (Phase 02)
**Status**: Accepted — 2026-10-17, implemented in Phase 02; ratify in the Phase 02 PR review. **Context**: the kit's Phase 02 guide downloads plugins with `theia download:plugins`, includes `@theia/vsx-registry` and (via Theia's examples) rebuilds native modules for Electron. Theia's downloader resolves extension dependencies to "latest compatible" and checks no integrity; the marketplace UI reaches whatever registry it is configured for; the Electron rebuild needs `artifacts.electronjs.org` (D12) and rewrites the `node_modules` both apps share. `@theia/electron` 1.76.0 pins Electron 42.8.1, which has four high-severity advisories. **Decision**: (1) **No in-IDE marketplace**: `@theia/vsx-registry` is not part of either app (`tests/lint/theia-versions.test.ts` fails if it is added); extensions are only the pre-bundled allowlist (T19, ADR-010). (2) **Pinned, hash-checked plugins**: `config/vscode-plugins.json` pins each built-in plugin by version and SHA-256; `scripts/plugins.ts` downloads them from the Open VSX mirror named by `QE_VSX_URL`, verifies the hash, unpacks them (Theia 1.76 deploys only unpacked system plugins) and removes anything else from `plugins/`. Hashes change only through `node scripts/plugins.ts lock` plus review; the `vscode-plugins` workflow prints them where the registry is reachable. (3) **No native rebuild**: every native module Theia uses is Node-API (spike S1), so the same binaries serve Node and Electron. (4) **Electron security overrides**: Electron may be raised above the `@theia/electron` pin within the same major through the root `overrides` (now 42.11.10), checked by the same test. (5) The IDE learns its mode once at backend startup from validated `QE_*` variables (Electron is always `desktop`); invalid configuration exits with 78, and the runtime image defaults to `hosted` so a misconfigured pod refuses to start. **Alternatives**: `theia download:plugins` (no integrity, floating dependencies); marketplace pointed at the mirror (needs D7, still allows ad-hoc installs); rebuilding for Electron (network dependency, shared-module conflicts); staying on 42.8.1 until Theia 1.77 (which moves to Electron 44). **Consequences**: + reproducible, auditable plugin set; no registry traffic from the IDE; builds need no Electron headers; − hash pins are trust-on-first-use from open-vsx.org until the mirror exists; new extensions need a manifest change; Electron runs a version Theia did not test (covered by the Electron smoke test, revisited at each Theia upgrade).

## ADR-013 — Managed settings for desktop and local web (Phase 10)
**Status**: Accepted — 2026-10-28, owner's decision in Phase 10 (P10.6). **Context**: 09_LOCAL_AND_WEB_PARITY §6 and PHASE_10 §10.7 ask for organisation-managed settings on users' machines: on Windows under `HKLM\Software\Policies\QEWorkspace` (what Group Policy and Intune set), on macOS and Linux in a JSON file. Node has no registry API; the repository standard (04 §2) lets only `runtime-providers`, `broker-core` and the runner start processes. **Decision**: (1) One strict, Zod-validated shape on every OS: `controlPlaneUrl` (https), `openVsxUrl` (https; recorded for the extension supply, not used at runtime yet), `deniedCidrs` (the embedded broker's deny list for personal targets), `trustOnFirstUse` (default true), `telemetry`. Registry values are `ControlPlaneUrl`, `OpenVsxUrl` (REG_SZ), `DeniedCidrs` (REG_MULTI_SZ or comma-separated REG_SZ), `TrustOnFirstUse`, `Telemetry` (REG_DWORD 0/1). Files: `/Library/Application Support/QEWorkspace/policy.json`, `/etc/qe-workspace/policy.json`. (2) On Windows `qe-core` reads the key with the system's `reg.exe` (`%SystemRoot%\System32`, never from PATH): `spawnSync(file, ['query', key, '/reg:64'], { shell: false })`, fixed arguments, 5 s timeout, read-only, once per process. `extensions/qe-core/src/node/qe-managed-settings-registry.ts` is the only extension file allowed `child_process` (eslint `childProcessAllowed`). (3) Read outside hosted mode only (desktop and local web); hosted runtimes are configured by the control plane. The organisation's `controlPlaneUrl` wins over `QE_CONTROL_PLANE_URL`. (4) Fail closed: malformed values, unknown names or an unreadable file stop the app with exit 78 and a message naming the source and fields — a typo must not silently drop a deny list. A missing key or file means no settings. **Alternatives**: a JSON file under `%ProgramData%` on Windows too (no process, but not what Windows management tools set); a native registry module (a new native dependency). **Consequences**: + IT manages QE Workspace like other applications; + one validated shape for three OSes; − one process exception in an extension, reviewed with this ADR; − reg.exe output parsing (covered by a test against a real key on Windows).

## ADR-014 — A shared runner package for test commands (Phase 11)
**Status**: Accepted — 2026-10-30, with the owner's approval of the Phase 11 plan. **Context**: PHASE_11 runs tests in three places: the IDE backend (workspace runtime, desktop, local web), and on remote targets through the broker (hosted) or the embedded broker (desktop, local web). 07_SECURITY T11 requires structured argv, allowlisted frameworks and no shell concatenation. If each place built its own command, a selector could be checked in one and not in another. The dependency rules (04 §1) let extensions and broker-core share only `domain`, `contracts` and `client-sdk`, none of which may hold this logic (`domain` is entities and errors; `contracts` is wire schemas). **Decision**: (1) A new library package `packages/runner` (`@qe/runner`) holds the run model (`TestRunRequest`, `TestSelector`, `RunState`, results), the framework adapters (`RunnerAdapter`: discovery and run commands as `{ file, args, cwd }`, parsing of their output) and selector, run-id and environment validation; Phase 11 adds the streaming JUnit parser. It is pure: no processes, files or network — callers start the command (`spawn` with `shell: false` locally; the broker's single quoting helper remotely). (2) Dependency rules: `runner ← domain`; `broker-core` and `extensions/*` may depend on `runner`. (3) Only frameworks with an adapter can be run (`Frameworks`; pytest first, Maven Surefire in P11.6). (4) Every user value becomes one argv element and is checked first: paths relative and confined to the project, without shell syntax or a leading `-`; node ids by PHASE_11's pattern; marker expressions one argument, length-limited; run ids UUIDs; extra environment upper-case names, never loader, shell or framework start-up variables. Coverage threshold 90 % (security-critical). **Alternatives**: the logic in `contracts` (mixes wire schemas with command building); in each caller (three copies of T11's checks); remote runs built by the control plane only (the desktop's personal hosts have no control plane). **Consequences**: + one place builds and checks every test command; + the broker never accepts a command line from a client, only a structured request; − one more package in the dependency graph.
